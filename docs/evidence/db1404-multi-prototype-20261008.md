# DB1404 多原型候选召回复核（2026-10-08）

## 范围与结论

- 本轮只做本地 CPU 多原型索引和候选短名单复核；未训练模型、未调用付费识别 API、未改 HTTP 契约、未部署服务器。
- 当前并非严格意义上的“模型过拟合”：线上粗筛只使用每类一张主图，且导入的一张异形图也未参与粗筛。PDF主要提供编号与中文释义映射，当前代表字图来自 `数据集/DB1404`。
- 新索引扫描 DB1404 的 **1,404 类 / 445,272 张**图片，每类先剔除距中心最远的 10% 候选，再用确定性的最远点遍历选 8 张代表图；选样用 8×8 块特征，检索用 16×16 灰度特征。最终为 **11,232 个原型**，无不可读图片，构建用时 184.840 秒。
- 重点复核 `东巴字图片_按中文含义命名/` 的 50 张图。按历史复核方式将短边图等比放大至长边 512 后，top-200 从本地重建的单主图 **34/50** 提升至 **42/50**；相对“主图+既有异形图”的 36/50 也提高 6 条。原图不放大时为 35/50 → 42/50。
- 50 张目标图在其正确类别源目录中没有逐字节完全相同样本，也没有相同 16×16 特征样本；排除完全相同 SHA-256 后仍为 42/50。因此本轮没有发现直接复用同一源文件造成的命中泄漏。
- 仍漏 8 条（长边 512 口径）：`举、懒、死、舞、跌、躲、雨、靠`。该结果是**短名单召回率**，不是外部模型 top-1 准确率，更不是手机实拍准确率。

- 索引：`runtime/glyph-prototypes/index.json`（被 `.gitignore` 排除），5,351,017 字节，SHA-256 `7907194cd061fc8e0f2933e2e89008fc473f03ee3e2a91f9f6ddbad9e8b03515`。
- 长边 512 的 50 图评测 JSON SHA-256：`3918c3076e9c4d4450eda6188e6aac37ba812c99bebfe6ea80d417f21505dd57`。
- 50 图目录按评测脚本“文件名 + NUL + 原始字节”计算的 SHA-256：`dd6414457ae1eeeb913afa19502f941e0afb3fa5d8dea1775117e6b937350676`。算法与图片整理证据中的清单指纹不同，不能直接比较。
- 评测记录的排除完全重复后的多原型平均排序耗时 687.527ms、最大 1,146.300ms。单独冷载入测量为 0.099s，首查 1,034.696ms，热查 728.797ms；`tracemalloc` 跟踪峰值 13.909MiB。它是本机 Python 分配峰值，不等于服务器 RSS。
- 评测不发送或持久化用户拍照；仅读取用户指定的本地 50 图和本地 DB1404。索引只记录选中源文件相对路径、特征和 SHA-256，不含凭据。
- 当前索引仍是本地实验产物，服务器没有 DB1404 全量源目录，不能把本地路径直接接入线上。下一步必须生成可部署的选中原型图片包、保留无索引回退，再做同一 50 图和实拍留出集复核后才能部署。
